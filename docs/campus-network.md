# 专题 · 校园 Wi-Fi 慢，SIM 正常：怎样定位

**目标：** 区分无线接入、校园策略和运营商路径；理解限速技术怎样影响上传与下载。**前置：** [握手与吞吐](training/03-handshake.md)、[测速案例](training/13-performance.md)。

## 1. 新证据把范围缩到哪里

“换 SIM 后下载比较正常”值得优先调查接入网络相关差异，但不是最终归因。以下链路中，换 SIM 通常同时换掉多个部分：

```text
同一台客户端 ── 校园 AP 无线链路 ── 无线控制器/认证策略 ── 校园出口 ── 运营商路径 ── VPS
             ╲ 手机 USB/热点 ─── 移动基站/运营商核心网 ── 移动出口 ── 另一条路径 ─╱
```

SS 或 TCP 入口在 SIM 上是否也成功、是否只在校园失败，需要分别记录。不能把一次下载正常推断成所有协议、UDP 和所有时间段均正常。

## 2. 不需要解密，也能分类与限速

设备可以依据认证用户、SSID、VLAN、IP、端口、TCP/UDP 等可见信息，把数据放进不同策略类别。应用识别还可能使用连接行为或可见握手元数据，但识别有误差；并非看到加密就能知道具体内容。

举例：控制器可分别给某用户的下行 TCP、上行 TCP、下行 UDP、上行 UDP 设置额度。于是同一节点的 TCP 下载慢、UDP 承载的 QUIC 较快，在技术上完全可能。这不需要破解 TLS。Cisco 的官方设备文档展示了按用户/SSID、方向及 TCP/UDP 的带宽控制能力；**这是机制实例，不是本校园采用 Cisco 或启用了该规则的证据**。参见[双向限速指南](https://www.cisco.com/c/en/us/support/docs/wireless/5500-series-wireless-controllers/113682-bdr-limit-guide-00.html)。

## 3. 限速具体怎样实现

常见模型是令牌桶：以速率 `r` 增加发送额度，最多存 `B` 字节额度；发送一个包需要相应额度。`r` 限制长期平均速率，`B` 允许短时突发。刚开始快、几秒后慢，可能与突发额度消耗有关，也可能有其他原因，不能仅凭曲线确定。

| 机制 | 超出额度时的行为 | 用户可能观察到 |
| --- | --- | --- |
| Shaping，整形 | 暂存到队列，按速率放行；缓冲满仍可能丢包 | 速度趋于上限，排队延迟增加 |
| Policing，监管 | 丢弃或降低优先级标记，取决于配置 | 丢包、重传、TCP 降低发送速率 |
| 调度 / 优先级 | 各类别竞争链路时获得不同服务次序/份额 | 高峰期某些流更慢，空闲时差异减小 |

这些模型可作用于单用户、单流或聚合流量。单用户总额度与每连接额度不同：多开连接可能只是共享同一额度，不会增加总带宽。整形和监管的官方解释见 [Cisco QoS](https://www.cisco.com/c/en/us/td/docs/routers/ios-xe/quality-of-service/quality-of-service/m_qos-plcshp-oview-0.html)。

以 2 Mbps 出口为例，已有 1 MiB 数据排在队列前方，单是排空它就需约 `1 × 1024² × 8 / 2,000,000 = 4.19 秒`。这解释了下载时交互延迟突然变高的一种原因；真实设备的调度、AQM 和队列大小需实测。

## 4. 没有人限速，也可能发生

无线频谱由附近设备共享。信道竞争、干扰、重传、低速客户端占用 airtime、AP 负载和省电策略都会影响有效吞吐。AP 向多台终端发数据与单终端上传的队列/竞争条件不同，不保证对称。信号格数和 Wi-Fi 显示连接速率不能替代应用吞吐。[Cisco 无线吞吐测试指南](https://www.cisco.com/c/en/us/support/docs/wireless/catalyst-9800-series-wireless-controllers/221766-validate-wi-fi-throughput-testing-and.pdf) 提供相应测量框架。

如果同一 Wi-Fi 下 QUIC 稳定快而多种 TCP 入口稳定慢，“无线链路对所有流量都有约 2 Mbps 硬上限”的简单解释就不充分。不过随机损失与不同拥塞控制仍可能造成差异，不能直接排除无线因素。

校园出口拥塞、跨网互联、回程路由、NAT、MTU 与 IPv4/IPv6 的不同，也都可能随换 SIM 一起改变。纯无线改善不一定修复校园出口问题。

## 5. 不修改服务器的对照计划

以下是下一次手工验收方案，**本轮没有自动执行真实节点测速**。固定同一台电脑、客户端核心与配置、节点、目标文件、单连接/并发数、载荷和 IP 协议族；暂停其他下载。用短时小文件先确认，不长时间占用网络。

| 对照 | 主要减少哪种混杂 | 仍不能证明什么 |
| --- | --- | --- |
| 校园 Wi-Fi 与同校园有线口（如允许） | 减少无线射频影响 | 两口可能处于不同 VLAN / 用户策略 |
| 校园 Wi-Fi 与手机 USB 共享 | 保持电脑/核心相同，移除该电脑的 Wi-Fi 接入 | 运营商与路径仍同时改变 |
| 校园 Wi-Fi 与 SIM 手机热点 | 保留电脑 Wi-Fi 使用，改变接入/出口 | 热点与校园 AP 的环境不同 |
| 同 AP 不同距离、频段、时段 | 看无线条件和负载相关性 | 时段也改变出口负载 |
| 同网的普通允许 HTTPS 与代理 HTTPS | 判断是否所有目标都慢 | 目标和路径必须记录，不能直接等同 |

按“校园 → SIM → 校园”交替，每种条件 3–5 次，记录成功率、下载/上传、开始耗时与样本范围。不要让测速 App 自动选择不同服务端后还当作严格对照。不要在报告里公开校园账号、SSID/BSSID、真实节点地址或订阅链接。

若校园有线与 Wi-Fi 都慢、SIM 正常，应优先找共同出口/策略/路径；若校园有线正常、Wi-Fi 慢，优先看无线段或 WLAN 专属策略。这些都是排查优先级，不是逻辑上唯一的原因。

## 6. 按瓶颈选择改进

- 无线争用/干扰：在允许的条件下比较合适频段、AP 位置或有线接入；先保留对照数据。
- 校园分用户/分类限额：向网络管理员核对套餐、策略和误分类；加密算法不能突破聚合容量上限。
- 路径损伤/拥塞：比较运营商路径与已启用入口的稳定性；未来维护窗口再考虑不同线路/节点。
- 实际 CPU 加密瓶颈：才进入 [AES 与 ChaCha 的对照](training/08-shadowsocks.md)，同时测端点 CPU，不能只看速度。
- 客户端选择：可给不同接入环境准备不同偏好的配置；url-test 测的是指定 URL 延迟，不会自动发现“握手快但下载慢”。带宽感知选择需要另行设计有流量预算的探测，目前未实现。

没有修改端口、伪装类别、校园设施或生产核心。下一步最有价值的是把网络对照补齐，避免同时换算法、核心与接入网后失去解释能力。

## 检查点

1. 学校必须破解代理加密才能区分 TCP/UDP 吗？不必，外层协议可见。
2. SIM 正常能否证明服务器永远没问题？不能；它只降低某些全路径共同瓶颈解释的优先级。
3. AES-256 比 AES-128 的“256 大一倍”，下载会翻倍吗？不会，数字指密钥位数。
4. 本地给所有协议限速的实验是否证明校园只限制 TCP？没有；还需要分类规则或严格对照证据。
