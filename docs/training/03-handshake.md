# 03 · 握手、首字节与持续吞吐

**目标：** 把“慢”拆成可测的阶段。**前置：** 01–02。

## TCP + TLS 的简化时序

```text
客户端                   代理服务器                  网站
  | -- SYN ----------------> |
  | <- SYN/ACK ------------- |
  | -- ACK ----------------> |  TCP 建立
  | <---- TLS 握手 --------> |  身份与密钥协商
  | -- 代理认证 + 目标 -----> |
  |                          | -- 连接目标 ----------> |
  | <-------------- 应用响应经代理返回 --------------- |
```

TLS 1.3 全新握手通常需要一个协议往返；实际总耗时还包含 TCP、DNS、代理认证与目标响应，且某些阶段可以合并。会话恢复、连接复用、0-RTT 条件各不相同，不能把所有协议都写成固定的总 RTT。0-RTT 有重放约束，不应为追求数字随意打开。参见 [TLS 1.3 RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html)。

QUIC 使用 UDP 承载，但自身包含加密握手、可靠流、确认、丢包恢复和拥塞控制。应用使用 QUIC 并不意味着“丢包就不管”。不同 QUIC 流可避免 TCP 连接层的跨流顺序阻塞，但仍共享路径容量与拥塞约束。参见 [RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html)、[RFC 9002](https://www.rfc-editor.org/rfc/rfc9002.html)。

## 延迟和速度回答不同问题

| 指标 | 含义 | 常见误解 |
| --- | --- | --- |
| TCP connect | 到接收端口的连接建立耗时 | 不是完整代理认证 |
| TLS handshake | TLS 会话建立耗时 | curl 访问网站时可能测的是目标网站 TLS |
| TTFB | 到响应第一个字节的时间 | 包含目标服务处理时间 |
| goodput | 有效负载字节 ÷ 耗时 | 不包括重传等线上总字节 |
| UDP loss / jitter | 接收损失与时延变化 | 不能由 ICMP ping 完整替代 |

下载的发送方主要在远端，上传的发送方主要在本机。两个方向的队列、限速、发送算法、接收窗口和路由可以不同。即使损失发生在“上传方向”，也可能损伤下载确认包。因此简单的“哪边丢包只影响哪边”不成立。

窗口型瓶颈的直觉是 `吞吐 ≤ 有效在途字节 / RTT`。例如仅允许 64 KiB 在途、RTT 100 ms，窗口上限约 5.24 Mbps。现代窗口缩放和拥塞控制比这个模型复杂；它用于提出检查方向，不用于反推出真实线路丢包率。参见 [TCP 拥塞控制 RFC 5681](https://www.rfc-editor.org/rfc/rfc5681.html)。

## 练习与检查点

一个 2 MiB 文件若总耗时 9 秒，goodput 约为 `2 × 1024² × 8 / 9 / 10⁶ = 1.86 Mbps`。如果首字节用了 8 秒，主要问题是开始阶段；若首字节仅 0.2 秒、后续持续慢，优先看数据阶段。

本地报告里的 `first_chunk_ms` 是读到首个 **64 KiB**，不是精确 TTFB，也不是 TLS 握手时间。不能用它给握手算法排名。继续：[REALITY](04-reality.md)。
