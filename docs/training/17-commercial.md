# 17 · 从个人节点到多人服务，缺的是什么

**目标：** 能评估扩展成本，不把增加网站等同于平台完成。**前置：** 15–16。

协议核心可以继续作为数据转发部件，但商业服务通常需要独立的控制系统。以下是架构规划，**本仓库没有实现或验证商业平台**。

```text
用户端 ← HTTPS 配置分发 ← 控制系统
  ↓                        ├─ 账户与独立凭据
多个地域/供应商节点         ├─ 配额、账单与权限
  ↓                        ├─ 节点配置版本与撤销
目标网络                   └─ 监测、客服与事件处理
```

## 能力不是简单相加

| 能力 | 个人节点 | 多人服务新增责任 |
| --- | --- | --- |
| 身份 | 单一所有者 | 每用户独立、可撤销、避免共享管理员权限 |
| 订阅 | 单私有链接 | 分用户授权、泄露追踪、短期或可撤销凭据 |
| 配额 | 云商总量 | 一致计量、限额、异常流量处理 |
| 容量 | 单节点预算 | 隔离噪声用户、容量冗余与迁移 |
| 发布 | 手工窗口 | 灰度、回滚、版本兼容与审计 |
| 可用性 | 个人容忍 | 明确 SLO、告警值守、故障沟通 |
| 安全 | 单人秘密 | 控制面最小权限、租户隔离、内部威胁 |

用户门户、订阅系统和代理管理 API 是不同安全边界。不能为了做漂亮网站，把核心管理 API 直接暴露到公网。计费和监测系统的宕机也不应立即切断所有已有数据连接；应定义过期、缓存与撤销的一致性策略。

## 先做哪一件事

先完成单节点恢复演练和真实客户端验收，再考虑第二个独立故障域与切换；之后才评估多用户凭据与控制面。网站只是交互界面，主要难点是权限、隔离、一致性和运维。

商业化还涉及所在地业务资质、隐私、消费者权益、付款和云商使用政策等，需要针对实际经营地另行核实；本课程不作适用法律或许可结论。成本也应包含支持、冗余流量与事件响应，不能只用 VPS 月费估算。

检查点：十个账户共用一个 UUID 能否独立撤销一个人的访问？不能。如果单控制面泄露能下发所有节点的 root 命令，故障半径是否过大？是，应拆分权限和部署职责。
