# 15 · 长期稳定与六个九的代价

**目标：** 把“别卡”变成可观察、可恢复的工程目标。**前置：** 11、14。

## 为什么重启后看起来好了

重启会清空进程内存、连接、部分内核状态与缓存，可能暂时解除积累的问题。候选原因包括内存泄漏、文件描述符耗尽、连接追踪表接近上限、日志/磁盘满、CPU 长期饱和、异常 DNS 缓存或软件缺陷。也可能只是重启期间线路拥塞自行缓解，相关性不是因果。

没有证据时定时重启，会抹掉现场并制造必然中断。先采集趋势，再决定更新、资源调整、连接超时策略或受控进程重启。正常系统不应因为“运行时间长”就必然变慢。

## 最小观察面

| 指标 | 看什么 | 可采取的动作 |
| --- | --- | --- |
| 请求成功率与延迟 | 外部客户端端到端结果 | 区分节点故障和目标故障 |
| 内存与 OOM | RSS 趋势、memory.events、内核 OOM | 定位增长和上限，不盲目加 swap |
| CPU 与节流 | 单核利用率、cgroup cpu.stat | 判断 1 vCPU 预算是否足够 |
| FD / socket | 使用量、状态与连接数 | 查连接泄漏或异常并发 |
| conntrack | count 与 max、丢弃 | 查连接洪峰、超时策略 |
| 磁盘 / inode / 日志 | 容量、增长速率 | 轮转与备份保留策略 |
| 流量 / 证书 | 云计费额度、实际呈现证书到期 | 提前告警 |

`scripts/check-host.sh` 提供手工只读检查；其输出可能含地址和进程名，留在私有运维记录。Docker 重启策略处理退出的容器，**不会仅因 healthcheck 变成 unhealthy 自动修复**。本项目未部署无人值守的自动修复控制器。参考 [Docker restart policy](https://docs.docker.com/engine/containers/start-containers-automatically/)、[cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)、[conntrack](https://docs.kernel.org/networking/nf_conntrack-sysctl.html)。

## 六个九意味着什么

| 可用性 | 365 天允许不可用 | 30 天允许不可用 |
| --- | ---: | ---: |
| 99.9% | 8 小时 45 分 36 秒 | 43 分 12 秒 |
| 99.99% | 52 分 33.6 秒 | 4 分 19.2 秒 |
| 99.999% | 5 分 15.36 秒 | 25.92 秒 |
| 99.9999% | 31.536 秒 | 2.592 秒 |

这是时间型预算；请求型 SLI 则是成功合格请求/全部合格请求。两者不能混用。还要定义地点、测量窗口、成功阈值、计划维护是否计入，并保存不可用证据。参考 [Google SRE SLO 实施](https://sre.google/workbook/implementing-slos/) 与 [错误预算策略](https://sre.google/workbook/error-budget-policy/)。

单台低成本 VPS、单一出口、手动维护无法可信保证六个九。需要跨故障域容量冗余、客户端故障检测、预分发备用配置、分批升级、恢复演练和持续值守。探测间隔 120 秒本身就远超月度六个九预算；即使改成 1 秒，用户网络和目标网站仍不受你完全控制。

## 练习与检查点

制定个人节点的初始目标，例如“每月端到端合格请求成功率 99.9%，故障 10 分钟内发现”，明确这是**目标、尚未测得的服务承诺**。每周检查资源趋势，每月隔离恢复加密备份，每次更新保留旧镜像与撤回路径。

一次证书加载停机 5 秒是否满足六个九月预算？已经超出。优化需要改变维护/冗余架构，而非把文档里的可用性数字改大。继续：[安全](16-security.md)。
