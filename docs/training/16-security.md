# 16 · 安全来自边界与验证

**目标：** 知道保护谁、信任谁、出事后撤销什么。**前置：** 10–12。

## 威胁与对应控制

| 风险 | 当前控制 | 剩余工作 |
| --- | --- | --- |
| 未授权使用节点 | 随机协议凭据、负例测试 | 泄露后的轮换与旧版本撤销 |
| 中间人 | TLS 链/域名检查、REALITY 公钥负例 | 设备时钟与客户端信任配置 |
| 容器越权 | 非 root、只读、drop ALL、无 socket | 宿主和 Docker 的更新 |
| 私网目标滥用 | 服务端规则拒绝私网与 metadata 地址 | 额外出口隔离、DNS 重绑定等高级验证 |
| 配置泄露 | Git 外状态、文件权限、加密备份 | 人员权限、终端剪贴板和分享习惯 |
| 订阅链接泄露 | 高熵随机路径、TLS、关闭访问日志 | 撤销链接，并单独撤销节点凭据 |
| 供应链风险 | 官方镜像固定摘要、工具哈希校验 | 持续漏洞跟踪与升级实验 |

这些控制降低风险，不构成渗透测试合格证明或“绝对匿名”。DNS 解析后的目标过滤、IPv6、复杂分流与不同客户端仍需专门验收；应用层规则不是完整网络隔离的替代品。

## VPN 不会消除所有信任

运营商仍可观察你连接某个节点的流量特征；节点运营者/云商可观察连接元数据。目标站看到出口地址。应用 HTTPS 通常保持客户端到网站的加密，但明文 HTTP、恶意终端、浏览器账户与指纹不会因使用代理自动安全。

客户端系统代理不一定覆盖所有应用；`ipv6: false` 也不是操作系统级 IPv6 kill switch。需要分别测试浏览器 DNS、系统 DNS、IPv6、WebRTC、断线后的应用行为。无 DIRECT 回退只约束进入本核心的流量。

## 密钥生命周期

DNS token、SSH 私钥、节点密码、订阅凭据和 age 解密身份分别保存。服务器放 age 接收公钥，解密身份离线保管；备份包加密后也要定期恢复验证。若凭据进入聊天、共享日志或公开提交，安排轮换，而不是只删那一行历史。

本轮未操作任何真实凭据或生产部署。旧凭据轮换会影响正在工作的客户端，应在维护窗口同时更新服务端、私有订阅与设备，并撤销复用同一秘密的旧 release。

## 发布代码前的练习

```bash
python3 scripts/scan-secrets.py
```

这只检查高置信模式，不能识别所有秘密。实际发布还使用仓库外私有 denylist，比对部署身份和已知敏感值；检查暂存文件、历史、附件与构建产物。扫描通过不等于数学上的“绝无泄漏”。本仓库从干净目录首次建 Git，未复制真实状态或原始截图。

检查点：固定镜像摘要是否意味着永远安全？不是；它保证选中内容稳定，不能阻止后来发现漏洞。参考 [Mihomo 安全策略](https://github.com/MetaCubeX/mihomo/security) 与 [Docker 日志轮转](https://docs.docker.com/engine/logging/drivers/local/)。
