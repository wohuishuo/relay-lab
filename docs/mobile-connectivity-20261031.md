# 手机连接故障与独立日常配置 — 2026-10-31

这次处理的是“多数入口完全连不上，能连上的入口速度正常”。结论来自同配置、不同路径的对照；没有把电脑实测写成手机已修复，也没有继续新增 Cloudflare/CDN 入口。

## 当前证据

| 对照 | 结果 | 能说明什么 |
|---|---|---|
| REALITY、AnyTLS、Trojan、SS + ShadowTLS、XHTTP、WS、直连 gRPC：直接建立 TCP | 7/7 超时，连接未建立 | 失败早于代理认证；继续改密码或调拥塞算法没有针对这一步 |
| 上述 7 个节点，保留服务器地址、TLS 校验、原凭据，经已有 TUIC 连接 | 7/7 完成证书校验并取得 HTTPS 204 | 对应服务、凭据与转发能工作；差异在进入服务器的路径和来源 |
| HY2、TUIC：各 3 次小 HTTPS 请求 + 1 个不同站点 | 各 4/4 成功 | 本次电脑所在网络可用；不代表长期可用率或吞吐量 |
| 原 gRPC-over-HY2 | HTTPS 204 | 它依赖 HY2，不是第三条独立入站路径 |
| IPv6 TCP：4 个现有入口 | 4/4 超时 | 本次也没有验证出可用的 IPv6 TCP 备用路径；没有据此修改防火墙 |
| 主核心、SS 侧车、订阅服务 | 运行；采样未见容器 OOM/重启；约 550 MiB 内存可用 | 当次没有资源耗尽的迹象，不能据此排除长期泄漏 |

结果见 [连接矩阵](../reports/connectivity-20261031.json)。curl 的 `time_connect` 在 SOCKS 测试里主要反映到本地 SOCKS 端口，不能拿它冒充到 VPS 的握手耗时；因此另外做了直接 TCP socket 检查。

**已定位：当前维护电脑到节点的直连 TCP 路径无法完成建连。** 经 TUIC 对照会改变路径和来源，所以它不能单独指出是哪台设备、哪个运营商、来源过滤还是回程策略。当天更早的一次有限抓包曾看到服务端收到 SYN、发出 SYN-ACK 后没有完成握手；这个观察也不能证明 SYN-ACK 到达了手机。没有证据将其归因于手机里的某个 App。

同日厂商另外确认了物理宿主故障并紧急维护。之前记录的整机停顿和 RCU 告警必须与这件事一起解释；内核栈采到诊断进程的 AppArmor 调用，不足以证明诊断程序引发了整机停顿。13:00 UTC 前后服务可访问，但没有用“能访问”代替厂商维护完成的通知。

这意味着换一种 TCP 协议名称、继续在同一 IP 上开端口，未必会得到新的可用路径。保留当前已测通的入口可以改善日常选择；它**没有修复那 7 条直连 TCP 路径**。所有协议仍共享一台 VPS 和一个宿主故障域。

### 后续退化样本：没有只保留成功结果

13:09 UTC，从服务器本机经实际代理入口取得 HTTPS 204，耗时 0.044629 秒。13:11:08–13:11:58 UTC 的外部复测期间，核心网络命名空间的 UDP 收发、错误、接收缓冲错误计数均无增长，相关 UDP 防火墙计数也未增长。**这一轮外部请求没有到达代理核心**；继续调核心内存或解密参数不能修复这一阶段。还不能仅凭这些计数区分客户端出站、传输路径、云侧过滤与宿主维护的具体影响。

这些失败与观测保存在[后续失败报告](../reports/mobile-path-regression-20261031.json)。新订阅在 12:57 UTC 已经通过外部 HTTPS 下载验收；该验收不意味着之后路径一直可用。没有因为失败而偷偷回滚成 DIRECT，也没有把它们统计成成功或零速下载。**当两条 UDP 入口同时不通时，新 Auto 同样不能恢复连接。**

13:22 UTC 左右，未修改同一手机配置、未重启代理核心，再次经该自动组下载 mobile、stable、legacy 三份订阅全部获得证书校验通过的 HTTPS 200，且内容一致；错误路径返回 404。这验证了当时至少一条入口恢复，不能据此宣布两个协议均已长期稳定，也不能确认厂商维护已经结束。

## 独立手机配置做了什么

原订阅仍保留全部入口。新 `mobile.yaml` 走同一条保密订阅父路径，日常仅包含这轮测通的两个独立入口：TUIC 和 HY2。经 TUIC 包装其他协议只用于诊断，没有把这些依赖关系包装成额外冗余节点。

- `JP-MOBILE → JP-MOBILE-AUTO`。自动组使用 `url-test`，检查间隔 30 秒、超时 8000 ms、切换容差 150 ms。它比较小请求延迟，不测带宽，不保证每次请求都成功。
- 不再让手机自动组持续探测本轮失败的 7 个 TCP 入口。它们仍在原订阅里，可在网络路径恢复后独立复测。
- 自动组不包含 DIRECT。显式 GLOBAL 组也指向 JP-MOBILE，避免初次切到全局时默认落到直连；国内分流仍要求使用规则模式。
- 沿用小型国内域名直连表，例如 `qq.com`、`wechat.com`。这些显式直连域名返回真实 DNS 地址；未知域名的 DoH 经过自动组，节点域名解析使用独立的加密解析器。
- 没有大型远程 GeoIP/GeoSite 下载，没有开启浏览记录、公开控制 API 或取消证书验证，也没有替手机强行写入桌面 TUN 参数。

这轮 TUIC 的一次首次小请求耗时 6.65 秒，后续三个请求成功。因此 **5 秒手动测速 Timeout 不总等于完全不可用**。8 秒检查窗口减少这一类误判，但无法让确实不通的 TCP 路径恢复。

国内域名表是可审查的例外表，不覆盖全部微信 CDN、IP 直连媒体或所有国内 App。DIRECT 会让相应服务看到普通网络出口。没有声称已经完成手机 WebRTC、IPv6、系统 DNS 或微信通话的实机验收。

## Clash Mi 导入与设置

真实链接只在私有交付文件里，不能提交到 GitHub。以下使用的是 Clash Mi 官方手册的设置名称；手机界面与应用版本可能有差异。

1. 保留当前能用的订阅并保持连接，添加新的**手机订阅链接**。订阅端口的直连 TCP 当前也可能不通，首次下载可以借助原来的 HY2/TUIC 连接；也提供了本地 `mobile.yaml` 作为导入备份。
2. 选中这个新配置，使用 **规则 / Rule** 模式。代理页将 **JP-MOBILE 选为 JP-MOBILE-AUTO**。日常不要把 JP-MOBILE 固定在某个具体协议上。
3. 在 **核心设置 → DNS** 中关闭 **DNS 覆写**，使本订阅的 DNS 配置生效。保留原先能够工作的系统 VPN/TUN 接管设置；本订阅不包含 TUN，**不要为了关闭 DNS 覆写而一并关闭整个 TUN 接管**。
4. 在应用设置里若有延迟测试超时，使用 **8000 ms / 8 秒**。这控制手动测速；订阅自动组已经配置了自己的 8 秒超时。
5. 保持证书校验开启。不要开启“忽略证书错误”，也不要给节点打开 `skip-cert-verify`。
6. 应用新配置后检查代理组当前成员，并实际打开一个需要代理的站点，再检查微信文字消息/图片。连通后再测试通话；不要把一次测速数字当作所有 App 都可用的验收。

如果客户端允许查看最终生效配置，应看到 `JP-MOBILE-AUTO` 的 `type: url-test`、仅 TUIC/HY2 两个成员、`timeout: 8000`，以及 DNS `nameserver` 的 `#JP-MOBILE-AUTO` 后缀。只更新远程订阅不能保证 App 保存的全局模式、手动选择、DNS 覆写也被更新。

回退：切回原订阅即可；其内容、凭据和服务器监听没有改变。故障测试中两条入口都不可用时，请求会失败，不会自动泄露到直连。

官方依据：[Clash Mi DNS 覆写说明](https://clashmi.app/guide/provider-faq)、[Clash Mi FAQ](https://clashmi.app/guide/faq)、[应用设置源码](https://github.com/KaringX/clashmi/blob/main/lib/app/modules/setting_manager.dart)、[Mihomo url-test](https://wiki.metacubex.one/config/proxy-groups/url-test/)、[v1.19.31 实现](https://github.com/MetaCubeX/mihomo/blob/v1.19.31/adapter/outboundgroup/urltest.go)。这些说明不证明手机当前已经开了错误选项。

## 生成与复现

```bash
python3 scripts/export-mobile.py \
  --input /private/current-client.json \
  --output /private/mobile.yaml \
  --candidate JP-TUIC --candidate JP-HY2 --balanced

python3 scripts/test-mobile-local.py \
  --input /private/mobile.yaml --core /private/mihomo \
  --state /private/new-mobile-test --fault
```

候选名称必须来自你自己当前网络的逐入口验收；生成器不会凭协议名称宣布节点可用。测试使用小型真实 HTTPS/DNS 请求，会产生少量网络流量。临时控制 API 仅绑定回环并使用随机密钥，输出不含节点凭据，测试结束会关闭自己的核心进程。

发布前在隔离的 Caddy 容器中执行了“新增路由 → 回退 → 再新增”的证书校验和内容检查。生产使用 `SIGUSR1` 热加载订阅配置，事先启用独立回退计时器，外部下载验收成功后解除。核心和订阅容器 ID、启动时间、重启次数保持一致；原订阅和 legacy 内容哈希保持一致。不存在公开的 `/mobile.yaml` 路由。详见[发布验收](../reports/mobile-publication-20261031.json)；它记录发布时的成功，不覆盖后来的路径失败。

工具的订阅链接轮换逻辑同时更新同一保密父路径下的 config、legacy、mobile 路由，避免轮换后旧的伴随链接仍然有效；有专门的回归测试。本次没有轮换正在使用的链接。

服务器探测无法替代手机到节点的路径测量；自动选择必须由持有配置的客户端执行。单 VPS 加协议切换无法保证 99.9999% 在线，更不能消除宿主维护或所有入口共同失效。
