# RelayLab release and research plan

Execution: primary agent only. The user explicitly authorized continued work without waiting for review. No production SSH, changes, reboot, DNS mutations, subscription changes, or production load tests in this task. Existing private project remains untouched.

Goal: create a private GitHub repository with reusable deployment tools, an attractive Chinese training manual, reproducible local networking experiments, and evidence-backed answers to the observed asymmetric throughput and SS failure.

Architecture: preserve the pinned upstream proxy core and optional static subscription service. Build a separate sanitized source tree; all generated credentials and test runtime state stay outside Git. The documentation site is static and can be served locally, with no production management endpoint. Failover examples are generated offline and must not change the live subscription.

- [x] First-run installer: interactive input or private settings files, dry-run plan, new-state guard, explicit prerequisites for firewall and recovery, fixed images/tools, fail-stop flow, reusable client export and optional subscription. Test missing prerequisites, unexpected existing state, failed commands, and successful execution sequencing.
- [x] Client modes: manual / fallback / URL latency selection examples with no DIRECT fallback; test generated config using the pinned core. Do not replace the user's live profile.
- [x] Local experiments: isolated networks, unique project names, controlled HTTP upload/download and request latency, bounded transfer budgets, protocol authentication, directional impairments where supported. Preserve every outcome, version, test condition and uncertainty.
- [x] SS investigation: prove classic SS works locally without a plugin; test wrong cipher/password and TCP/UDP failures separately. Explain why a missing TCP handshake cannot be diagnosed as password failure.
- [x] Training: system map, packet journey, core, each enabled protocol, DNS, Cloudflare DNS API, certificates, Docker/firewalls, subscription vs control plane, performance, stability/SLO, failover, threat model and commercial architecture. Each lesson has objectives, exercises, checkpoints and authoritative sources.
- [x] Visual presentation: custom cover, diagrams, linked learning paths, searchable static documentation build, responsive rendering verification.
- [ ] Publish: create private repository using authenticated account, neutral project name respecting upstream naming notice, noreply commit identity, no secrets in first history. Push only after checks. Verify remote HEAD, privacy and CI status.

## Evidence rules

Screenshot throughput is a user observation with unknown endpoint/device/concurrency, not a controlled benchmark. Public-host root cause remains unconfirmed unless existing captures prove the specific layer. Local loss/rate experiments illustrate mechanisms, not the real WAN's exact cause. A six-nines target is a budget of roughly 31.5 seconds/year; a single VPS cannot support an evidence-based six-nines guarantee.

## Review focus

Production impact; credential-bearing logs/URLs; Docker namespace and port isolation; timeouts and partial output; false benchmark success or misleading averages; source/version drift; unsafe installer reruns; generated failover health != capacity; private repository does not replace sanitization.

## Execution notes

All work is performed locally and directly. First-run orchestration is tested with mocked side effects for success/failure order; real cloud installation remains unverified. Full protocol, wrong-credential, certificate, image lifecycle, subscription and encrypted-backup tests use actual local components. Directional measurements retain all 150 successful transfers and model limitations. Client failover is tested by removing the primary local ingress and then stopping all local ingresses; no live client profile is changed.
